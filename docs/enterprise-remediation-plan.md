# Qwen3Guard 企业级生产平台整改方案

评估日期：2026 年 10 月 20 日。代码基线：`305f664`，包含当前工作区现有实现。

当前产品属于“真实模型驱动的功能验证平台”：输入、输出、批量审核和审计接口已经打通，但尚未形成可安全运营的企业服务。整改应保留已部署模型和已有检测能力，优先补齐访问控制、持久化、执行可靠性和可信评测，再改造控制台。

这里将“API 检测能力”定义为两条业务链路：业务系统通过 API 实时审核内容；平台接入企业大模型 API，持续执行安全评测与回归。传统 SQL 注入、网络漏洞扫描不属于本期产品范围。

## 评估依据与运行基线

已检查前后端源代码、Docker 编排、现有数据结构和运行首页，并通过本机 HTTP 接口核验运行状态。脱敏结果保存在 [运行基线](readiness-baseline-2026-10-20.json)。

| 核验项 | 实际结果 | 判断 |
| --- | --- | --- |
| 模型 | 三模型均已加载，CUDA，RTX PRO 4500 Blackwell | 可以复用，不需要重新部署模型 |
| 综合检测与输入检测 | 两个正常样例均返回 200、放行结果、审计 ID | 调用链真实可用 |
| 两次串行样例端到端耗时 | 约 1.75 秒、1.66 秒 | 仅冒烟观察；不能据此认定并发容量或 SLA |
| 未登录读取网关配置 | 200，包含 4 个完整密钥 | 上线阻断项；报告不保存密钥值 |
| 未登录读取运行配置、审计 | 均为 200 | 缺少管理边界与数据隔离 |
| OpenAPI | 42 个路径，无 securitySchemes | 接口目录存在，认证契约未建立 |
| 首页 | 基准准确率、演练提升、模型显存、网络地址占主要空间 | 以能力展示为主，缺少业务运营视角 |

此次只执行两次低负载正常内容推理，服务因此新增两条审计记录；没有执行删除、改策略、密钥轮换、全量评测或压测。权限写操作风险由代码审查确认，未在运行服务上执行破坏性验证。

## 已有功能的处理结论

| 模块 | 已实现 | 不完善之处 | 整改方式 |
| --- | --- | --- | --- |
| 输入与输出审核 | Gen 模型、规则融合、PII 检测、分类及审计 | 缺少会话上下文、动作统一、异常状态与策略版本 | 保留推理，重构决策服务 |
| 流式检测 | 对完整文本做 Token 标注、定位截断点、SSE 推送 | 完整推理后重放；没有上游边生成边检查 | 保留离线诊断，新增真正流式护栏 |
| 批量审核 | 1～50 条逐条检测，线程转移与批次落盘 | 实际为循环串行，缺少任务状态、取消与部分失败恢复 | 同步小批量加资源限制；大任务异步化 |
| OpenAI 风格接口 | chat 与 moderation 端点 | chat 丢弃历史，只取最后 user/system；moderation 响应不符合宣称的标准结构 | 明确支持子集，建立客户端契约测试 |
| 网关与密钥 | 创建、禁用、删除、策略绑定、进程内 QPS 限制 | 明文密钥、无生命周期和权限域；许多配置未执行 | 重构为应用接入中心与数据面认证 |
| 参数调试 | 预设、实时修改、单样例 A/B | 配置直接覆盖生产，无发布版本、审批、灰度与回滚 | 拆分实验草稿、评测与正式发布 |
| 审计与复核 | 原文、结果、分类、检索、导出、人工标记 | 全局可见、原文明文保存、可直接删除、缺少操作者与版本 | 数据库审计、默认脱敏、权限化复核 |
| 题库与评测 | CRUD、导入导出、同步自测 | 检测逻辑读取同一题库标签，缺少独立测试集与任务管理 | 隔离评测数据，任务化、版本化 |
| 报告 | 静态基准与审计汇总 | 测试准确率混称合规率；演示种子和真实调用没有可靠区分 | 分开运营报表与离线评测报告 |
| 控制台 | 八模块可路由、真实接口驱动 | 单体 HTML/JS、长文案、重复功能、缺少用户/应用上下文 | 以任务流程重建信息架构 |

## 必须先修复的生产缺口

### 身份与权限边界

`app/main.py:1220` 的网关读取、修改、密钥创建和删除接口没有认证依赖；运行配置、题库与多项自测接口也缺少管理鉴权。审计接口虽然调用 `resolve_request_key()`，但没有按调用方限定可见对象；即使开启 API Key 验证，也不能等同于租户隔离。

整改：

- 管理面使用用户登录会话，数据面使用应用凭证；业务 Key 不具有策略发布、审计清空或密钥管理权限。
- 建立组织、项目、应用、环境与成员关系，资源查询由服务端限定作用域。
- 首期角色：平台管理员、项目管理员、安全运营、开发接入、只读审计；原文查看和导出另设权限。
- 本地账户支持安全口令哈希、登录限速、会话过期与撤销；企业 SSO/OIDC 后续接入。Cookie 会话使用 HttpOnly、Secure、SameSite，状态变更接口配置 CSRF 防护。
- 生产数据接口默认强制认证；演练凭证仅用于独立沙盒。已有管理路由同步保护，避免只保护新路由留下旧入口。
- 当前 chat 请求可由调用方设置 `guarded=false` 跳过护栏（`app/main.py:383`、`app/model_manager.py:548`）。生产防护是否启用必须由服务端应用策略决定，裸模型对比仅开放给授权沙盒角色。

这些问题对应 API 对象授权、身份认证、属性暴露和功能授权风险，可参照 [OWASP API Security Top 10](https://api-security.owasp.org/editions/2023/en/0x11-t10/) 制定访问控制测试。

### 密钥与接入治理

`app/platform_store.py:726` 将新密钥明文存储；`app/main.py:1221` 返回完整配置；前端 `app/static/app.js:892` 获取并缓存全部密钥。

整改：

- 新密钥只在创建时展示一次；持久化随机高熵密钥的安全摘要及标识前缀，校验采用常量时间比较。
- 增加有效期、作用域、应用归属、环境、限额、最后使用时间、轮换和撤销。列表、日志、导出中不返回完整凭证。
- 凭证优先通过 Authorization/X-API-Key 传输，逐步移除 URL 参数与可冒充身份的 Key ID 调用方式。
- 旧密钥兼容迁移与轮换必须有切换窗口；未知历史暴露情况需按已暴露凭证处置。迁移前先完成管理员登录，避免控制台失去入口。
- 出站上游凭证需要用于发起请求，不能只存哈希，应由独立密钥引用与加密存储管理。

### 检测决策的可信性

`app/model_manager.py:229` 在模型输出解析失败时默认 `Safe`。`app/security_shield.py:434` 加载评测题库的 `expected_unsafe` 标签，再在 `:586` 和 `:599` 影响最终判定。因此现有满分结果不能证明模型对未知样本的泛化能力。

`app/security_shield.py:534` 的自定义放行词分支只有 `pass`；风险分数主要由固定值与权重组合得到，不能当作校准后的概率。输出审核还混合了问题与回答的规则判断，需要专门验证“危险问题但安全拒答”等情况。

整改：

- 模型异常、空输出、解析失败统一为 `indeterminate/error`，由版本化策略决定阻断或人工复核；不得伪装成安全结果。
- 统一决策 `allow / block / mask / review` 与执行状态 `completed / timeout / error`；同时记录模型判定、规则命中和最终策略动作。
- 从线上检测中解除对评测标签的依赖；确需使用的业务规则单独维护来源、审核和版本。
- 规则、模型类别、行业分类映射分别可追踪；多个风险可同时返回，给出命中片段及位置。
- 明确输入、输出、上下文三种审核语义；识别拒答不能只依据“抱歉”“安全”等词。
- 字符长度与 Token 预算同时校验；完整多轮 messages 进入检测，超长内容采用显式拒绝或带覆盖范围说明的分段策略。
- PII 返回类型与位置，支持真正执行 block/mask/audit；风险分数明确标为策略评分。

### 执行可靠性与真实流式能力

`app/main.py:496` 等异步路由内直接执行同步推理；模型共用 `RLock`。`/v1/guard/batch` 虽转移到线程，内部仍逐条循环。`default_timeout_ms`、三阶段网关开关、`pii_action`、上游地址和 Webhook 未在实际主执行链路中使用。

`app/main.py:862` 在创建 SSE 迭代器之前完成整段检测；chat 接口在完成生成后每 12 字符切片发送。现状应准确标注为“完整内容审核/结果回放”。

整改：

- 将推理隔离到受控 Worker 或现有推理服务适配器，配置有界队列、并发额度、排队截止时间、推理截止时间、拒绝过载和优雅停机。
- 不通过增加 Web worker 数量重复加载 GPU 模型。先保留现有模型加载方式，独立出调用边界，再根据实测优化批处理。
- 超时后不能只取消 HTTP 等待却释放仍在执行的 GPU 槽位；Worker 必须报告真实结束或支持中止。
- Redis 承担跨实例限流和预算计量；分别计数 HTTP 请求、检测条目、Token 消耗，批量不能按一次便宜请求绕过资源限制。
- 各配置拥有校验、能力状态和执行证据；未实现的配置禁止展示为已生效。
- 真正流式网关读取上游增量，缓冲未审核片段，在审核通过后释放，命中后停止释放并取消上游。定义审核窗口、累计上下文、背压、断连和最终审计。
- 对已经放行的前缀无法撤回；高风险应用默认整段审核，实时应用明确接受窗口语义，不能承诺零泄漏。

同步阻塞调用与异步路由的处理边界参照 [FastAPI 并发文档](https://fastapi.tiangolo.com/async/)。具体吞吐量以现有 GPU 的受控负载测试确定。

### 数据持久化与审计

`app/platform_store.py:632` 在日志不存在或不可解析时植入演示记录；每次请求重写 JSON，默认仅保留 2,000 条，启动又从剩余记录重建 Key 计数。这不适合计费、长期趋势或跨实例一致性。`record_audit_entry` 存原始内容，缺少 HTTP request_id、操作者、租户、模型修订和策略版本。

整改：

- PostgreSQL 保存业务对象与事务，迁移脚本版本化；审计按时间分区或归档，分页索引覆盖租户、应用、时间和结果。
- 分开内容检测事件、管理操作日志与计量流水；保留期删除不应改变累计计量。
- 默认只显示脱敏摘要；原文按项目策略选择不保留或加密保留，访问和导出均记录审计。
- 决策事件与投递任务通过事务性 outbox 持久化，异步送往检索和通知系统；持久化失败时的行为必须可配置、可观测。
- 演示、调试、评测、生产分别标记来源；旧记录无法判断来源时标为 `legacy_unknown`，禁止自动算入生产指标。
- 复核以追加事件记录，不覆盖原始机器判断；人工加白不能直接生成全局规则，需形成受作用域约束的策略草稿。
- 提供备份、恢复验证、归档和审计完整性检查。当前无需先引入复杂数据湖。

## 控制台整改

首页以“哪些应用在使用、服务是否稳定、哪里需要处理”为中心。统一项目/环境选择器、时间范围和刷新时间，将 GPU、版本、网络地址移入系统运行页面。

| 新导航 | 核心工作内容 | 主要页面 |
| --- | --- | --- |
| 运营总览 | 观察生产调用与异常 | 请求量、成功率、P50/P95/P99、阻断率、超时率、未处理事件 |
| 应用接入 | 让一个业务系统完成接入 | 应用列表、负责人、环境、凭证、策略绑定、限额、接入验证 |
| 检测记录 | 查清一次请求的处理过程 | 多条件列表、request_id 搜索、分阶段详情、脱敏内容、复核入口 |
| 安全策略 | 配置并安全发布检测行为 | 策略列表、规则编辑、版本差异、评测门禁、发布记录、回滚 |
| API 资产与评测 | 持续检测企业模型 API | 目标端点、连通性、数据集、任务、进度、历史报告、趋势 |
| 风险事件 | 把发现的问题处理完 | 分级、负责人、处理状态、证据、备注、关闭与复开 |
| 开发者中心 | 稳定集成与排障 | 实际契约生成的文档、错误码、SDK 示例、沙盒调试、配额说明 |
| 系统管理 | 企业治理与运行维护 | 成员角色、模型端点、依赖健康、审计保留、告警渠道、操作日志 |

页面标准：

- 使用中性色、紧凑表格、统一图标和有限状态色；减少 Emoji、渐变、宣传标语、大段说明和重复入口。
- 列表具备服务端分页、筛选、排序、可保存视图和统一详情抽屉；操作按角色可见，但权限始终由后端验证。
- 明确加载、空数据、错误、无权限、过期数据状态。未加载指标显示“—”，没有样本显示“暂无数据”，不能默认 100%。
- 首页不把离线准确率称为线上合规率；生产数据不混入沙盒、演练、种子和自动评测数据。
- 表单验证、提交中状态、失败恢复和变更差异可见；策略发布、凭证撤销提供影响范围和操作记录。
- 控制台调试使用当前用户权限和独立沙盒作用域，避免下载业务 Key 后在浏览器中代替用户执行。
- 现有单体页面逐页替换，后端契约稳定后采用 TypeScript 与组件化前端；保留旧路由重定向，不一次性重写模型层。

## 需要新增的业务能力

1. **企业 API 资产管理**：登记模型服务地址、协议、请求/响应映射、凭证引用、负责人和环境；支持连接测试、健康状态与版本。
2. **自动安全评测任务**：对已授权目标 API 发送版本化测试集，调用现有 Guard 审核回答；支持定时、并发限制、预算、停止、断点、重试与逐项结果。限制目标域名/IP、重定向与解析后的地址；内网目标通过明确白名单授权，防止连接功能成为任意代理。
3. **可信评测体系**：调试集、规则参考集、回归集、独立盲测集隔离；近重复去重、人工标注、模型/规则/联合结果分别报告，报告携带数据集哈希和模型/策略版本。使用 Guard 评分的目标 API 评测必须标明评审来源，并抽样人工复核。
4. **策略发布管理**：草稿、校验、评测、审批或有权限发布、影子运行、按应用灰度、回滚。单次请求固定使用同一版本。
5. **风险工单与告警**：从检测记录创建事件，分配责任人并追踪处理；Webhook 签名、重试、去重、投递状态和失败队列。
6. **可观测与容量治理**：统一 request_id/trace_id，记录鉴权、排队、模型、规则、审计和上游调用耗时；面板显示超时、429、5xx、队列、GPU 和通知失败。日志、指标与追踪的边界采用 [OpenTelemetry signals](https://opentelemetry.io/docs/concepts/signals/)。
7. **交付与恢复能力**：可重复安装、固定依赖、数据库迁移、健康探针、备份恢复演练、灰度部署、故障回滚与操作手册。

## 技术边界与迁移方案

第一阶段采用模块化单体管理服务加独立推理执行边界，避免过早拆成大量微服务。

```text
业务系统 ── 数据面 API ── 身份/额度 ── 策略决策服务 ── 推理适配器 ── 已部署模型
                              │             │
管理控制台 ── 管理面 API ── 用户/项目权限      └── 检测事件/计量/outbox ── PostgreSQL
                              │
                              ├── Redis 限流与任务调度
                              └── 评测 Worker ── 授权企业模型 API
                                                  │
                                                  └── Guard 评审与人工复核
```

核心实体：`organizations`、`projects`、`memberships`、`applications`、`api_keys`、`model_endpoints`、`policies`、`policy_versions`、`detection_events`、`operation_events`、`usage_records`、`datasets`、`dataset_versions`、`evaluation_jobs`、`evaluation_items`、`incidents`、`webhook_deliveries`、`outbox_events`。租户资源携带 `organization_id/project_id`，应用数据携带 `application_id/environment`；时间统一 UTC，界面按用户时区展示。

迁移步骤：

1. 为当前配置、题库、审计和基准做可验证备份；保留已存在的工作区改动，不覆盖业务数据。
2. 创建数据库 schema 与迁移工具，导入有来源标记的数据；种子样例隔离，冲突及损坏文件报错并输出迁移报告，不默默重置。
3. 对账记录数量、来源、应用归属及检测动作；凭证迁移后不再写回明文 JSON。
4. 先上线管理登录、凭证管理和新控制台，再强制数据面鉴权；设定旧调用方式迁移期限。
5. 对现有 `/v1/guard/*` 保留兼容适配层；有破坏性的字段变化使用版本化新接口和弃用说明。
6. 切换前只读旧存储并处理最后增量，失败则回退服务和数据库快照；不能将新写入数据直接丢弃后回退。

## 阶段与上线门槛

| 阶段 | 交付重点 | 验收门槛 |
| --- | --- | --- |
| P0 受控试运行 | 管理鉴权、应用隔离、安全凭证、持久化、检测异常语义、真实指标、受控推理队列 | 未认证/越权请求拒绝；密钥不泄露；异常不判 Safe；重启不丢数据；两个应用数据互不可见 |
| P1 生产业务闭环 | 应用接入与控制台、版本策略、真实流式、企业 API 评测任务、告警复核、契约与回归测试 | 应用接入→检测→记录→复核→策略发布可完整操作；任务可取消恢复；流式断连不留任务 |
| P2 规模化运营 | SSO、配额计量、多实例、调度公平性、容量压测、备份恢复、持续监控 | 明确支持的负载下满足协商的 SLO；多实例限流一致；恢复及回滚演练通过 |

预计工程量：P0 约 10～15 人日，P1 约 20～30 人日，P2 约 10～20 人日，属于初步估算。真实流式模型能力、业务集成数量、SSO 环境和数据迁移质量可能改变工期。下一步以首轮任务拆分后排期，不把此估算当交付承诺。

暂定服务目标：月度可用性 99.9%，稳态服务端错误率低于 0.1%；这是设计目标，需要多实例、监测和故障演练支撑。延迟与吞吐必须按输入 Token 档位、检测模式、并发和批量大小建立容量曲线，再确定正式承诺；当前没有证据支持页面上“120 QPS 配额”等于实际处理能力。

所有阶段都需执行身份越权、敏感字段泄露、持久化恢复和接口兼容测试；生产开放前还必须验证模型不可用、数据库不可写、Redis 不可用、队列满、请求超时及流式断连行为。

首轮任务及验收条件见 [开发任务清单](development-backlog.md)。
